> 状态:✅ 已完成(2026-09-28 第 34 轮闭环)

## 描述(即 bug)

用户通过「开始打磨」创建的打磨任务(type='requirement',R3.F1 起=真实 Task 行,有工作台 /tasks/{id})不出现在 /manage/tasks 任务列表:dashboard_views.py:135 附近 type 白名单只收 dev/test/release。DB 实证今日 2 条打磨任务(id 975/977)在列表不可见,用户误以为任务创建失败/丢失。

**用户拍板(2026-09-28)**:方案 A——打磨任务纳入 /manage/tasks 任务列表展示。本分片即规格落点(用户裁定,不再征询)。

## 实现要点(根因 + 修复方案)

- 根因:后端 `GET /api/dashboard/tasks/{task_type}` 的 task_type 白名单(dashboard_views.py:123-208,过滤条件 140-144)排除 requirement;前端 /manage/tasks 固定挂 dimension='dev'(ManagePages.tsx:57-69;api dashboard.ts:111-114)。
- 修复目标口径:**/manage/tasks 能看到打磨任务(type='requirement')**,与 dev/test/release 并列;行点击进 /tasks/{id} 工作台(既有行为)。实现方式按现有结构最小改动,由实施 subagent 读码后定,参考方向:
  - ① 后端:task_type 白名单放行 requirement(或等价的列表口径扩展),`created_by=me` + 可见项目 scope 过滤保持不变;列表返回字段对 requirement 行不缺关键项(类型徽章数据源)。
  - ② 前端:任务维列表支持混合类型展示或类型筛选(全部/开发/测试/发布/打磨,按现 DimensionPage 结构最小实现);类型徽章「打磨」沿用现有 bdg 配色体系;状态列沿用现有 statusMap(requirement 任务 status 枚举与 dev 相同;R3.F2 的 display_status 派生字段为**可选增量**——响应里有则优先展示,缺失优雅回退,不得阻塞在本分片上)。
- ⚠ 冲突红线(并行在途会话):R3.F2 会话正在改 task_service.create_polish_task / display_status 与 TaskDetail/ProjectTaskList/RequirementDetail 三处映射——**本分片禁改这些文件**;只动 dashboard_views.py 与 DimensionPage/ManagePages/api dashboard.ts 一线。若发现必须动 task_service 才能达成,停下上报主 agent,不得自行扩面。
- 后端以 `--reload` 运行(改码即热载,验证前 curl /health 确认热载成功);前端门禁 = tsc + build。
