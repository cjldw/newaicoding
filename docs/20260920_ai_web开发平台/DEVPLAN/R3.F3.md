# R3.F3 — 修复 BUG-073 容器泄漏:任务终态后容器不回收(4 路径收口)

> 状态:✅(2026-09-29 实施完成,加固完成,14/14 单测全绿)
> 关联 BUG:BUG-073(用户报障「窗口管理泄漏:任务跑一段时间,容器会比任务多」)
> 诊断底稿:.scratch/fix-analysis.md § BUG-073(2026-09-29,实证 4/4 运行容器全孤儿,0 个 running 任务)
> 归属模块:M3(任务域)/ M5(Runner/容器域)

## 描述(即 BUG-073)

任务进入终态(done/cancelled/timeout/failed)后,容器未被可靠销毁;retry 叠加新容器不清旧。长跑环境下容器数持续多于存活任务数。实证快照(2026-09-29 12:40):docker 4 个 Up 的 devbox 容器,对应任务全部终态(timeout×2 / cancelled×2),DB running 容器 4 行全为孤儿。

## 根因(4 条泄漏路径,file:line 以诊断日代码为准)

1. **retry_task 不检查/不清旧容器**(task_service.py:1105-1136):直接 schedule_and_start 建新容器行,旧 running 行无人收;finish_task 收容器只取 `.order_by(id.desc()).limit(1)`,历史行漏网。实证:task 279938f7(cancelled)叠 2 个 running 容器。
2. **request_stop 仅下发不等回报**(container_service.py:177-192):stop_container 发出即返回,无超时兜底;Runner 侧失败或回报丢失 → DB+docker 双驻留。实证:e17584d3/830af6e6(timeout)容器 2173ba6b17e7/9b13fe6af4a9 双驻留。
3. **Runner 离线分支只标 stopped 不销毁**(container_service.py:183-188):注释「待 R16 对账」但 R16 对账未实现,Runner 恢复后无补发 stop。
4. **无启动时孤儿对账**(main.py:96-123 lifespan):重启后不扫 DB running 容器与 docker 真实状态差异,不补发 stop。

## 实现要点(五个子项)

- **F2.a request_stop 改等回报 + 超时兜底**:下发后等 Runner container_stopped 回报(超时 60s);超时未回报 → 置 container.status=destroyed + destroyed_at(container_service.py:177-192)
- **F2.b Runner 离线分支入补收队列**:Runner 重连(runner_ws.py register)时对该 Runner 上 status=stopped 且 destroyed_at IS NULL 的容器补发 stop;或挂 lifespan 周期巡检(60s)
- **F2.c retry_task 先清旧容器**:start_task 前查 Container.task_id==task 且 status IN (running,creating),逐条 request_stop + 置 destroyed(task_service.py:1105-1136)
- **F2.d 启动孤儿对账**:lifespan 启动一次性扫描 containers.status IN (running,creating):docker 侧不存在/已退出 → 置 destroyed;仍存在且对应 task 已终态 → 补发 stop(main.py:96-123)
- **F2.e finish_task / sweep_timeouts 收所有 running 容器**:去掉 limit(1),改 where status=running 全量循环 request_stop(task_service.py:1045-1084 / 1150-1156)

**风险与口径**:F2.d 会销毁「任务已终态但用户可能仍在终端里用」的容器(实证 5cf413bb2dda 属 task 279938f7 已 cancelled 但可能在被使用)——实现按口径「终态任务不应有活容器」执行,存量清理前单独向用户确认;测试期间不得重启 8000 生产后端、不得 kill 真实容器。

### 加固记录(2026-09-29)

#### F2.d fail-safe 修复

**问题**:原 `inspect_container_docker` 占位返回 None,而 `reconcile_orphan_containers` 把「无 inspect 结论」当成「容器不存在」置 destroyed——生产会把活容器全部误标 destroyed(数据损坏级)。

**修复**:
- `inspect_container_docker` 返回约定改为:
  - `None`: 未知(inspect 调用失败/超时/未实现) → 调用方 fail-safe 跳过,绝不置 destroyed
  - `{"exists": False}`: 明确证据表明 docker 侧不存在 → 可安全置 destroyed
  - `{"exists": True, ...}`: docker 侧存在
- `reconcile_orphan_containers` 改为 fail-safe:
  - inspect 返回 None 或异常 → 跳过并 log 警告,绝不置 destroyed
  - 仅当 inspect 返回 `{"exists": False}` 时才置 destroyed
  - task 已终态时补发 stop(状态收敛交给 F2.a 超时兜底)

**测试**:
- `test_lifespan_inspect_unknown_skips_container`: inspect 返回 None 时 running 容器不被误杀
- `test_lifespan_inspect_exception_skips_container`: inspect 抛异常时 running 容器不被误杀

#### F2.b 接线

**问题**: `resend_stop_for_offline_containers` 已实现但未接入 `runner_ws.py` 的 Runner 注册/重连流程。

**修复**:
- 在 `runner_ws.py` 的 register 成功后立即调用 `resend_stop_for_offline_containers(db, runner.runner_id)`
- 使用独立 db session(`async_session_factory()`)避免与主消息循环 session 冲突
- 补发失败不阻塞连接(try/except 包裹,仅 log warning)

**测试**:
- `test_runner_ws_register_calls_resend_stop`: 验证 runner_ws 主函数在 register 流程中调用 resend_stop_for_offline_containers
