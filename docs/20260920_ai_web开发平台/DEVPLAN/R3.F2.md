## 描述(即 bug)

用户指令:「需求创建后,开始打磨,确保 container 启动好了,没有启动好,页面状态显示启动中」。

「开始打磨」创建 requirement 任务后,`create_polish_task` 调度容器成功即置 `task.status="running"`,但容器经 Runner 异步拉起(Runner WS 下发 `start_container` 后立即返回),`container_started` 回报前 `containers.status="creating"`、`tasks.container_id=NULL`。该窗口期(实测可达数十秒~分钟级)前端任务工作台/任务列表/需求详情关联任务表格全部显示「运行中」——用户无法区分"容器还在拉起"与"已在运行"。

## 根因(分析底稿 `.scratch/fix-analysis.md` § 第 33 轮)

1. `task_service.create_polish_task` L143-144:调度成功立即 `status="running"` + `started_at`(R3.F1 语义,本身正确——不回滚任务)
2. 任务详情/列表 API 均不返回容器状态,前端只认 `task.status`
3. 前端状态映射(TaskDetail.tsx `VP_ST` L58-77 / ProjectTaskList.tsx `statusMap` L22-29 / RequirementDetail.tsx L444-453 直出原始串)无「启动中」概念

| 阶段 | task.status | container.status | 现状显示 | 期望显示 |
|---|---|---|---|---|
| 调度后即刻 | running | creating | 运行中 ❌ | **启动中** |
| 回报后 | running | running | 运行中 ✅ | 运行中 |
| 拉起失败 | running | failed | 运行中 ❌ | **失败** |

## 实现要点(方案)

**后端派生 `display_status`,前端只消费**(单一事实源;不动 task.status 枚举,状态机/超时清扫/R37.F5 零影响):

1. `backend/app/services/task_service.py` 新增 `_derive_display_status(task) -> str`:
   - `task.status != "running"` → 原值透传(pending/done/failed/timeout/cancelled 等)
   - `running` 且容器 `creating`(或无容器行)→ `"starting"`
   - `running` 且容器 `running` → `"running"`
   - `running` 且容器 `failed` → `"failed"`
   - **其余容器状态(如 destroyed)→ 兜底回 `"running"`**,不显示启动中(防运行中任务容器被回收后状态卡「启动中」)
2. 任务详情 `GET /tasks/{task_id}`(api/tasks.py)与 `task_service.task_brief` 输出加 `display_status` 字段(需求关联任务列表 `/requirements/{rid}/tasks` 若走 task_brief 则自然覆盖,实施时核实)
3. **列表接口防 N+1(硬约束)**:`task_brief` 若需查容器状态,列表路由必须一次性批量查 `containers`(task_id IN …)建 map 传入,或对 relationship 用 selectinload 预载;**禁止每行单查**
4. 前端三处落点:
   - `TaskDetail.tsx`:`VP_ST` 增 `starting: { label: '启动中', bdg: 'b-amber' }`;StatusBadge 对 `starting` 同样给 pulse dot 动画;wb-head 取 `display_status ?? status` 查映射(旧数据无字段时回退不崩)
   - `ProjectTaskList.tsx`:`statusMap` 增 `starting`(label 启动中,Loader2 spinner 同 running)
   - `RequirementDetail.tsx` 关联任务表格:改用 `display_status` + 补最小颜色映射
   - `api/tasks.ts`:类型声明补 `display_status?: string`
5. 波及面:dev/test/release 任务有容器的自然适用;无容器任务(若有)回退 task.status 无副作用
