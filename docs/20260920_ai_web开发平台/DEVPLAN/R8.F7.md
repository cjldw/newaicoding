# R8.F7:修复 BUG-081 容器回报丢失 + 对账误杀占位行(收养/护栏/复活)

> 编号:R8.F7 | 模块:M5(任务级容器 / Runner 对账)

> 状态:✅ 已完成(2026-10-08 晚 rd-fix 收口;backend 5+runner 2 新用例全绿,runner 全量 114/114,容器路径回归 18/18;runner 镜像/容器与后端均已重启,对账实测零误杀;verified 待用户复验)
> 前置:R8.F5(BUG-055)runner 侧 sync 上报已带 `qicheng.task_id` 标签,平台侧收养逻辑缺失(本分片补齐)

## 描述

WS 连接在 `start_container` 下发后、`container_started` 回报前断开(keepalive 超时族):回报发进死连接永久丢失;runner 重连注册触发 `handle_sync` 对账,按 container_id 比对 docker 清单,`pending-` 占位行永不匹配 → 被误置 destroyed。docker 容器实际活着,但平台台账判死 → 任务永卡「启动中」,对话/终端 9001。

## 实现要点

1. **`runner_service.handle_sync` 护栏 + 收养**(backend,重启即生效):
   - 护栏:`container_id` 以 `pending-` 开头的占位行**不参与**「不在上报 → destroyed」判定(占位行的生命周期 = container_started 提升 或 任务级清扫)
   - 收养:上报条目含 `task_id`(R8.F5 标签)且该 task 存在 pending 占位行 → 提升为真实容器(container_id 去重替换、status 按上报、`runner_host_port_*` 随上报端口回填,可空)
2. **`container_service.handle_container_started` 复活**:无 `creating` 行时,按 task_id 找最近一条 `pending-` 占位行(destroyed 亦可)且该 task 无 running 行 → 复活(替换 id/running/清 destroyed_at/写端口);真无行维持原 warning
3. **runner `local_container_states` 补 ports**:从 `running_probes` 带上宿主机端口映射(需镜像重建生效;旧 runner 少此键,平台侧 `r.get("ports")` 容缺)

## 测试验证逻辑

1. 收养:pending 占位行 + sync 上报(带 task_id/ports)→ container_id 替换、running、端口回填
2. 护栏:pending 占位行不在上报 → 状态不变(不被 destroyed)
3. 回归:真实 id 行不在上报 → destroyed(原语义)
4. 复活:handle_container_started 收到回报时行已被置 destroyed → 复活为 running
5. runner pytest:`local_container_states` 带 ports 键
6. 部署后真机:现网任务 4d0e3ce5 已数据修复可验证基础链路;断连重放场景由 1-4 锁定
