# R16.F4:修复 BUG-045 机器信息增强(Windows 内存为 0 + 字段扩充)

> 状态:✅ 完成(2026-09-24 第 22 轮闭环;BUG-045 verified 迁移 ISSUES.md)
> 模块:M5(Runner 侧 collect_machine_info)+ 前端展示(RunnerManagement 机器信息列);**后端零改动**
> 关联:BUG-045;用户指令 2026-09-24(rd-fix 第 22 轮:「修复下机器信息,目前内存是0,还可以获取多点信息么」)

## 描述(BUG)

- **复现**:Windows 裸跑 runner 注册成功后,Runner 管理页机器信息显示「内存 0GB」
- **实证**:`runners.machine_info = {"os":"windows","arch":"AMD64","cpu_count":16,"mem_total_gb":0,"docker_version":"27.0.3","self_container_id":""}`(2026-09-24 15:58 runner-local 首次上报)
- **根因(实施时读码确认)**:`runner/main.py` `collect_machine_info()` 内存采集疑用 Linux-only 途径(/proc/meminfo 或 os.sysconf),Windows 平台取值失败静默回退 0

## 实现要点

1. **`runner/main.py` `collect_machine_info()` 扩充**(纯标准库,Windows/Linux 双兼容;**逐字段独立 try/except,单字段失败置 None,组装时剔除 None 键——任何字段失败不得阻塞注册**):
   - `mem_total_gb` 修复:Windows 用 `ctypes.windll.kernel32.GlobalMemoryStatusEx`(MEMORYSTATUSEX 结构体,ullTotalPhys/2**30);Linux 维持既有途径(sysconf 或 /proc/meminfo)
   - 新增字段:
     - `os_version`:`platform.platform()` 截断 ≤100 字符(如 "Windows-11-10.0.22621-SP0")
     - `hostname`:`socket.gethostname()`
     - `ip`:UDP socket connect(`8.8.8.8:80`,不实际发包)`getsockname()[0]` 取本机出口 IP;失败置 None
     - `disk_total_gb` / `disk_free_gb`:`shutil.disk_usage(os.getcwd())`(runner 进程工作目录所在盘)
     - `cpu_model`:`platform.processor()` 截断 ≤80 字符(Windows 返回 CPU 族号串;可为空则剔除)
   - 既有 `os` / `arch` / `cpu_count` / `docker_version` / `self_container_id` 语义与键名不动(后端/前端既有消费兼容)
2. **后端零改动**:register 处理对 machine_info 原样 JSON 透传存储(既有行为),新字段自然落库
3. **前端 `RunnerManagement.tsx` `formatMachine()`**:机器信息列两行 mono 展示——
   - 行1:`CPU {cpu_count}核 · 内存 {mem_total_gb}GB · 磁盘 {disk_total_gb}GB`
   - 行2:`{os_version} · {hostname} · {ip}`(行2 任一字段缺失则不渲染该行;旧 runner 数据只有既有字段时优雅降级为现状一行)
   - **冲突红线:只动 formatMachine 函数及其调用的机器信息单元格渲染,不碰操作列/按钮/chip/弹窗(R31 并行实施范围,其 15:36 已改过此文件)**
4. **测试**:新增 `runner/tests/test_machine_info.py`——本机(Windows)实跑 `collect_machine_info()` 断言:mem_total_gb>0、disk_total_gb>0、hostname 非空、核心键(os/arch/cpu_count/docker_version)存在;结构断言不炸跨平台
