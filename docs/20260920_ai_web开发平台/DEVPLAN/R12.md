## PRD 引用

### 边界定义

- **做什么**:邀请(**手机号精确搜索**,R1 已去邮箱)/移除/角色变更
- **不做什么**:组织层级/跨项目权限继承/审批流/**邀请新用户注册**(平台注册邀请是超管职能,见 R19;本项目邀请仅面向已注册用户)

### 交互规则(权限矩阵)

| 操作 | owner | editor | viewer |
|---|---|---|---|
| 查看项目/需求/任务/代码(只读)/预览 | ✅ | ✅ | ✅ |
| 创建/编辑需求 | ✅ | ✅ | ❌ |
| 启动需求打磨任务 | ✅(需绑定 token) | ✅(需绑定 token) | ❌ |
| 评审需求(通过/驳回) | ✅(需绑定 token,通过时用其 token commit PRD) | ✅(同左) | ❌ |
| 创建/执行任务(dev/test/release) | ✅(需绑定 token) | ✅(需绑定 token) | ❌ |
| 用任务内终端/编辑器 | ✅ | ✅ | ❌ |
| 邀请/移除/改角色 | ✅ | ❌ | ❌ |
| 改模型配置(R13) | ✅ | ❌ | ❌ |
| 改项目 GitLab 绑定(R2) | ✅ | ❌ | ❌ |
| 归档/删除项目 | ✅ | ❌ | ❌ |
| 知识条目提升到平台级(R14) | ✅ | ❌ | ❌ |
| 转让 owner | ✅(降为 editor) | - | - |
| **以上全部操作(超管)** | **✅(R19:超管在所有项目自动等同 owner,含未参与项目;审计记 superadmin 身份;实现为项目级 Guard 的虚拟 owner,不做成员记录冗余,D16)** | 同左 | 同左 |

**"需绑定 token"**:执行该操作前,平台校验用户已绑定 GitLab token 且对该 repo 有 read+write 权限;未绑定则跳转个人设置页引导绑定(R1)。

### 异常与边界场景

- 项目必须 ≥1 owner
- 单项目成员 ≤ 50

### 验收标准

1. 权限矩阵每条可验证
2. viewer 写操作前后端双重拦截

### 接口契约

**接口契约** 总览——**响应结构**统一外层 `{"code": 0, "data": ..., "message": "ok"}`(错误时 `code` 为业务错误码、`message` 为提示文案);字段级结构以下方各接口小节的请求/响应示例为准:

| 接口范围 | 响应结构约定 |
|---|---|
| 本需求点全部接口(下方小节逐一列出) | 统一外层 `{code, data, message}`;分页接口 `data` 含 `{items, total}` |

#### 1. 成员列表

- **路径**:`GET /api/projects/{project_id}/members`
- **鉴权**:JWT(项目成员)
- **响应**:
  ```json
  {
    "code": 0,
    "data": {
      "items": [
        {
          "user_id": "uuid",
          "username": "string",
          "nickname": "string",
          "avatar_url": "string",
          "role": "owner",
          "invited_by": {
            "user_id": "uuid",
            "username": "string"
          },
          "joined_at": "datetime"
        }
      ]
    },
    "message": "ok"
  }
  ```

#### 2. 邀请成员

- **路径**:`POST /api/projects/{project_id}/members`
- **鉴权**:JWT(owner 或超管——超管按 R19 等同 owner)
- **请求**:
  ```json
  {
    "phone": "string",
    "role": "editor|viewer"
  }
  ```
- **响应**:
  ```json
  {
    "code": 0,
    "data": {
      "user_id": "uuid",
      "username": "string",
      "role": "editor"
    },
    "message": "邀请成功"
  }
  ```
- **错误码**:
  - `12001`: 用户不存在(提示"该手机号未注册;平台注册邀请由超管在「平台管理 → 用户管理」发起,见 R19")
  - `12002`: 用户已是项目成员
  - `12003`: 单项目成员数超限(>50)

#### 3. 移除成员

- **路径**:`DELETE /api/projects/{project_id}/members/{user_id}`
- **鉴权**:JWT(owner 或超管——超管按 R19 等同 owner)
- **响应**:
  ```json
  {
    "code": 0,
    "message": "移除成功"
  }
  ```
- **错误码**:
  - `12004`: 不可移除最后一个 owner

#### 4. 改角色

- **路径**:`PATCH /api/projects/{project_id}/members/{user_id}`
- **鉴权**:JWT(owner 或超管——超管按 R19 等同 owner)
- **请求**:
  ```json
  {
    "role": "owner|editor|viewer"
  }
  ```
- **响应**:
  ```json
  {
    "code": 0,
    "data": { /* 同成员列表项 */ },
    "message": "角色已更新"
  }
  ```
- **错误码**:
  - `12004`: 不可移除最后一个 owner(改角色时校验)
  - `12005`: owner 转让给非成员(必须先邀请)

#### 5. 转让 owner

- **路径**:`POST /api/projects/{project_id}/transfer-ownership`
- **鉴权**:JWT(owner 或超管——超管按 R19 等同 owner)
- **请求**:
  ```json
  {
    "new_owner_user_id": "uuid"
  }
  ```
- **响应**:
  ```json
  {
    "code": 0,
    "message": "转让成功,您已降为 editor"
  }
  ```
- **错误码**:
  - `12005`: 目标用户不是项目成员

### 服务端行为规格

#### 邀请成员

1. 校验当前用户是 owner
2. 根据 `phone` 查 `users` 表
3. 用户不存在 → 返回 `12001`(前端提示"该手机号未注册,请联系管理员邀请注册"——平台注册邀请是超管职能,R19;V1 不做邀请链接)
4. 用户已是成员 → 返回 `12002`
5. 校验单项目成员数 ≤ 50
6. 写 `project_members` 表
7. 调 GitLab API 把该用户加到**所有绑定 repo**为 Developer(遍历 `project_repos` 表,调 `POST /api/v4/projects/{repo_id}/members`,body `{"user_id": gitlab_user_id, "access_level": 30}`;30=Developer)
8. 返回成员信息

#### 移除成员

1. 校验当前用户是 owner
2. 校验目标用户不是最后一个 owner(查 `project_members` 表,`role='owner'` 的记录数)
3. 删除 `project_members` 表记录
4. 调 GitLab API 把该用户从**所有绑定 repo**移除(遍历 `project_repos` 表,调 `DELETE /api/v4/projects/{repo_id}/members/{gitlab_user_id}`)

#### 改角色

1. 校验当前用户是 owner
2. 若目标角色是 owner → 校验**不能移除最后一个 owner**(当前 owner 改为 editor 后,目标用户改为 owner)
3. 更新 `project_members` 表
4. 若改为 owner → 调 GitLab API 把该用户在所有绑定 repo 的权限改为 Maintainer(40);若从 owner 改为 editor/viewer → 改为 Developer(30)/ Reporter(20)

#### 转让 owner

1. 校验当前用户是 owner
2. 校验目标用户是项目成员
3. 事务:
   - 当前用户 role → editor
   - 目标用户 role → owner
4. 调 GitLab API 更新权限(当前用户 Maintainer → Developer;目标用户 Developer → Maintainer)

### 页面交互流程

#### 邀请成员流程

1. 用户点"邀请成员" → 打开对话框
2. 输入手机号 → 前端调 `GET /api/users/search?phone={phone}`(**手机号精确匹配**,R1 已去邮箱)→ 下拉显示匹配用户(无结果则提示"该手机号未注册")
3. 选择用户 → 选择角色(editor/viewer)
4. 点"邀请" → 调 `POST /api/projects/{pid}/members`
5. 成功 → 关闭对话框 → 刷新成员列表
6. 失败 → 显示错误提示(用户不存在/已是成员)

#### 改角色流程

1. 用户在成员列表点"改角色"
2. 打开对话框 → 显示当前角色 → 选择新角色
3. 点"确定" → 调 `PATCH /api/projects/{pid}/members/{user_id}`
4. 成功 → 关闭对话框 → 刷新成员列表

#### 移除成员流程

1. 用户在成员列表点"移除"(非最后一个 owner)
2. 弹出确认对话框
3. 点"确定" → 调 `DELETE /api/projects/{pid}/members/{user_id}`
4. 成功 → 刷新成员列表
