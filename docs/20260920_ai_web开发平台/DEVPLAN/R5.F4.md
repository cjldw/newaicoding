## 描述(即 BUG-074)

AI 对话流式回复开头重复一行,如「好的,Q1-Q4 已确认。……」连写两遍。落库 content 干净(id=326),重复纯发生在前端接收层。

## 根因

`backend/app/services/task_service.py:635-669` `_stream_event_to_chat` 对同一内容有两条并行 chat_delta 提取路径:
- 路径 A:`stream_event` → `content_block_delta`/`text_delta` 逐 token 增量(BUG-058 真 流式来源)
- 路径 B:`assistant` 事件的整块 `message.content[].text`(历史回退)

CLI `--include-partial-messages` 下每个 content block 结束必发一次 `assistant` 整块事件 → 后端两条路径都 `_broadcast_delta_smooth` → 前端 `TaskChat.tsx:258` `setStreamText(prev => prev + text)` 无去重 → 首块文本累加两遍(首 block 紧贴消息开头,观感为「开头一行重复」;后续 block 因有换行分隔不显)。

## 实现要点(方案 A,最小改动)

- `send_message_stream` 主循环维护标志 `seen_stream_delta = False`(每次调用重置):
  - 收到 `stream_event/text_delta` 广播后置 `True`
  - `assistant` 整块分支仅在 `not seen_stream_delta` 时返回 chat_delta(老版本 CLI 无 partial 事件的兜底语义保留);已见过 text_delta 则跳过广播
- 不动:runner 透传、落库路径(取 result 事件,本就干净)、前端累加逻辑、打字机平滑

## 测试验证逻辑(修复后回归)

1. **单测(Red→Green,tests/test_task_chat_stream.py 或邻近文件)**:按诊断 § 六构造事件序列——text_delta 逐 token(「好的,」+「Q1-Q4 已确认。」)+ 紧随 `assistant` 整块(同文本)→ 断言产出的 chat_delta 拼接文本中该句**只出现一次**;反向用例:仅 `assistant` 整块、无任何 stream_event(模拟老 CLI)→ 整块仍广播(兜底不回归)
2. **触碰面回归**:task_service / chat stream 相关既有 pytest 全绿(串行)
3. **真机冒烟**:后端重启部署后,真实对话一轮,回复开头无重复(用户下次对话自然复验即可)

## 风险与口径

- 若存在「CLI 有时只发 assistant 整块、不发 partial」的真实路径,方案 A 的标志位保证兜底仍走——不会回归成无流式
- 后端改动,部署需重启 8000(detached,循第 41 轮方式)
