# PRD:项目成员批量邀请

> 创建日期:2026-09-26
> 状态:**已确认**(2026-09-26,待确认清单已空)
> 关联:平台主 PRD R1/R12(项目三级角色与成员管理)

## 背景与现状

项目详情「成员」页现有邀请为**单个手机号添加**(owner 专属):输入手机号 → 精确匹配已注册用户 → 选角色 → 直接入库并同步 GitLab 仓库成员。效率低且无法浏览平台已有用户。

## 需求点

### R1:候选用户列表接口(owner 专属)

- 新增 `GET /api/projects/{project_id}/candidate-users`:分页 + 搜索(昵称/手机号模糊)
- 鉴权:项目 owner(超管旁路);复用 admin/users 的打码与过滤逻辑
- 返回标记:is_member(已是项目成员)、status;前端据标记禁选

### R2:批量邀请接口(整体事务)

- 新增 `POST /api/projects/{project_id}/members/batch`:入参 `{user_ids: string[], role: editor|viewer}`(owner/超管;单次 ≤50,去重)
- **整体事务语义(已确认)**:先全量校验(用户存在/active/均非项目成员/加入后不超 50 上限),任一不满足 → 400 整批拒绝并列原因;全部通过 → 单事务插入 + 审计 + GitLab 仓库成员同步
- 响应:`{added: n, users: [...]}`;失败 400 `{message, errors: [{user_id, reason}]}`
- **替换原邀请入口(已确认)**:前端「邀请成员」Dialog 改造为选择式,不再保留手机号直添

### R3:前端选择式邀请 Dialog

- `components/ui/Checkbox.tsx` 新组件(全站首个多选组件)
- 重构「邀请成员」Dialog:搜索框 + 候选列表(分页,checkbox 多选,已成员/disabled 置灰禁选)+ 统一角色选择(editor/viewer RadioGroup)+ 已选计数
- 提交:整体成功 → 关 Dialog + 成员列表刷新 + toast「已添加 n 名成员」;整批失败 → Dialog 内错误条(原因列表)
- 旧的单手机号搜索卡片逻辑移除

## 范围外

- 手机号直添入口(随替换取消;未注册用户仍走超管邀请注册)
- owner 角色批量授予(批量仅 editor/viewer;owner 变更走现有转让流程)
- 候选列表全选跨页(全选仅当前页)

## 异常场景

| 场景 | 处理 |
|---|---|
| 批量后超 50 人上限 | 整批 400「加入后成员将超上限(50)」,列超出人数 |
| 任一用户已是成员 | 整批 400,列该用户 |
| 任一用户不存在/已停用 | 整批 400,逐条列原因 |
| user_ids 为空/超 50/含重复 | 400 校验错误(前端禁提交兜底) |
| 候选列表接口非 owner 访问 | 403 |
| GitLab 仓库成员同步失败 | 沿用现有单邀请语义(成员已入库不回滚,同步失败不阻塞) |

## 确认记录(2026-09-26)

| 问题 | 结论 |
|---|---|
| 与手机号单个邀请的关系 | **替换**——邀请 Dialog 改造为选择式,不再保留手机号直添 |
| 角色指定 | **统一角色**(editor/viewer RadioGroup) |
| 成功语义 | **整体事务**(任一失败整批拒绝并列原因) |
| 停用用户 | **显示但禁选**(置灰标注「已停用」) |
